# 全站雲端戰績：房主上傳、匿名裝置代號、Cloudflare Workers 加 D1

戰績從各瀏覽器本機的個人紀錄，改成所有玩家共用的雲端資料庫，統計代表整體的角色勝率與回合數分布。

- **範圍是全站，不是個人。** 戰績頁的用途是評估角色與卡片的強弱，全站的樣本比個人的有意義；因此不做登入，也沒有「我的戰績」。
- **連線對局只由房主上傳。** 引擎在房主那裡，結果最可信；訪客也上傳會讓同一場被算兩次。單機對電腦的對局由本機上傳。
- **不登入，只有匿名裝置代號。** 每個瀏覽器自己產生一個隨機代號，伺服器只用它限流，沒有任何個人資料。每一場另有隨機的對局代號，伺服器對它有唯一限制，所以上傳失敗後補傳是安全的。
- **伺服器用 Cloudflare Workers 加 D1。** 免費額度夠用、不要求信用卡、閒置不會被暫停；驗證與限流寫成 TypeScript 放在倉庫的 `server/`，核心是一個輸入請求與資料存取介面的處理函式，測試用 Node 內建的 SQLite 外殼跑真正的 SQL。部署由本機的指令完成，不走 GitHub Actions。
- **沒有刪除與修改的對外介面。** 要清資料由站長在伺服器端處理，所以戰績頁拿掉了「清除全部紀錄」。
- **統計仍在瀏覽器端計算。** 伺服器只依版本回傳原始戰績，既有的統計函式不變。

## 為什麼要記下來

這個決定難以逆轉（資料已經在雲端、改範圍或換服務要搬資料），而且缺少脈絡會讓人意外：為什麼不做個人戰績、為什麼訪客不上傳、為什麼沒有刪除功能。

## 考慮過的替代方案

- **個人戰績加跨裝置同步**：需要身分機制（登入或同步碼），門檻與維護成本都高，而且回答不了「角色強不強」。
- **Supabase 或 Firebase**：免寫伺服器程式，但前者免費方案閒置約一週會被暫停，兩者的驗證規則都綁在各家的設定語言裡，不能像現在一樣放在倉庫裡用測試守住。
- **訪客也上傳、伺服器去重**：需要讓兩邊對同一場產生同一個代號，得在連線協定裡多傳資料；只讓房主上傳更簡單，也更可信。

## 後果

- 沒有防作假的強驗證：任何人都能送出格式合法的假戰績。目前只靠格式驗證、來源限制與限流壓低濫用；若日後成為問題，再考慮簽章。
- 本機舊戰績留在本機、不上傳、不再顯示，因為它們沒有去重資訊，會污染全站統計。
- 伺服器的角色清單要和遊戲的角色清單一致，新增角色時伺服器要一起改，測試會提醒。
