# 卡片行為統一為效果來源：時機一律走觸發窗口，卡片狀態存在每局的狀態槽

卡片與角色提供的行為原本散在 `scripts.ts`、`game.ts`、`combat.ts`、`combatStats.ts`、`ops.ts` 與 `TurnFlags`，引擎裡有十幾處依卡名或角色名的比對。決定把它們收進一個效果來源模組：一個條目就是一張卡或一位角色，條目內寫出它在各時機的行為；階段函式只問「這個時機、這位玩家有哪些效果」，不認得卡名。事件型的時機一律以觸發窗口呈現，卡片擁有的回合狀態放在這一局的狀態槽，回合開始由引擎統一清空。

## 考慮過的選項

- **維持內嵌的 hook 表**：打出、先手出招、成為追擊卡直接呼叫 hook，不開窗口。今天可行，因為這些時機各只有一個效果；但日後同一時機有第二個效果時，要回頭改階段函式，且玩家沒有排序權。
- **單一入口加上約二十個時機名稱的目錄**：進入點最少，但介面的寬度只是搬進目錄，且條目要分清楚「卡在場才問」與「離場後仍問」兩種處理器，用錯會悄悄改變規則。
- **宣告式條目，費用、每回合一次、條件寫成欄位**：新增卡最省力，但每張卡原本的細節順序，例如先檢查目標再付費、效果量為零時不錄發動影格，會被收進欄位語意而悄悄改變。第一版不做，等整個遷移完成、行為穩定後，再從 `c.effect` 往上收重複的樣板。
- **採用**：型別化的時機目錄與查詢目錄、條目層級必填的常駐位置、型別化的狀態槽。只有一個可發動的效果時，觸發窗口直接走效果自己原本的詢問，所以出招類時機改包成窗口後，目前的卡池下行為完全相同。

## 後果

- 常駐位置必須明寫，離場後仍要生效的處理器必須明寫 `lasting`。漏寫不會報錯，效果只是悄悄消失，所以每個這類處理器都要有對應的測試。
- 狀態槽存在這一局的 `GameState` 上，不能是模組層級變數，否則多局會共用。
- 「這張卡有沒有實作」由模組回答，涵蓋裝備與角色。
- 追擊階段的瞄準次數是程序自己的記帳，不屬於任何一張卡，留在追擊步驟裡。
