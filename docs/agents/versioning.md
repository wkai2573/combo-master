# 版本號維護規範

專案使用語意化版本（Semantic Versioning, `major.minor.patch`）。版本號直接呈現於遊戲首頁與戰鬥畫面頂端，用以供使用者與開發者辨識目前執行的遊戲功能與版本狀態。

## 1. 觸發時機

每次開發任務在交付與提交（Commit）時，應檢核是否符合以下升版條件：

### 必須升版
- **新功能（feat）**：新增卡片、新角色技能、新遊戲機制、新增或重構主要 UI 模組。
- **修復（fix）**：修復戰鬥判定、介面錯誤、顯示異常等 bug。
- **UI / 樣式微調**：調整對齊、版面跳動修復、色調或字型等影響終端視覺的變更。
- **卡表同步**：執行 `npm run table` 同步卡表數據產出 `src/data/cardTable.json`。

### 不強制升版
- 純內部重構（`refactor`，未改動任何外顯行為或介面）。
- 測試案例增減（`test`）。
- 說明文件修改（`docs`）。
- 議題筆記與規格草稿（`.scratch/`）。

---

## 2. 進位規則

| 變更幅度 | 升級位元 | 範例 | 說明 |
| :--- | :--- | :--- | :--- |
| **小修復 / 微調** | **Patch** (`+0.0.1`) | `0.10.0` → `0.10.1` | Bug 修復、單一文案修正、樣式細節調整。 |
| **新功能 / 新機制** | **Minor** (`+0.1.0`) | `0.10.0` → `0.11.0` | 新增卡片、完整功能實作、完成一組規格票券。 |
| **重大發布** | **Major** (`+1.0.0`) | `0.10.0` → `1.0.0` | 僅在使用者明確指示發布重大版本或架構顛覆時進位。 |

---

## 3. 變更與提交方式

1. **檔案範圍**：版本號儲存於 `package.json` 的 `version` 欄位。升版時必須同步更新 `package-lock.json`：
   ```bash
   npm version <newversion> --no-git-tag-version
   ```
   或直接編輯 `package.json` 後執行 `npm i --package-lock-only`。
2. **隨功能一併提交**：版本更動應包含在該次功能的 Git commit 之中（同一個 commit），不另外建立單獨的 bump commit。
3. **更新日誌隨版本一起**：玩家看得到的變化，在同一個 commit 於 `src/data/changelog.ts` 補一筆，用玩家的語言寫（不寫模組名稱與重構細節）。日誌版本會因純重構升版而跳號，這是預期的；`tests/changelog.test.ts` 只檢查格式、排序與不超過目前版本。
4. **不建立 Git Tag**：專案不另外打 Git Tag，版本由 `package.json` 與 `vite.config.ts` 自動注入的 commit hash 組合辨識。

---

## 4. 議題追蹤系統（.scratch/）關聯

當實作涉及 `.scratch/<feature-slug>/issues/` 的子票券時：
- 在票券完成結案（`Status: resolved`）時，於檔案底部的 `## Answer` 明確標記生效版本號：
  ```markdown
  已於 v0.10.0 生效。
  ```

---

## 5. Agent 任務收尾檢核清單（Checklist）

所有 Agent 在完成任務準備提交 Git Commit 前，**必須**逐項檢查：

- [ ] 1. 本次任務是否包含功能修改、問題修復、UI 微調或卡表同步？
- [ ] 2. 若是，是否已依進位規則遞增 `package.json` 與 `package-lock.json` 的版本？
- [ ] 3. 若變更是玩家看得到的（卡片、角色、規則判定、介面），是否已在 `src/data/changelog.ts` 最前面補上該版本一筆？純內部重構、沒有可見變化的升版不用補。卡表同步造成的變動逐張寫卡名，歸「調整」類。
- [ ] 4. 是否已執行測試與型別檢查（`npm test`、`npm run build`）確認通過？
- [ ] 5. 若有處理 `.scratch/` 票券，是否已在票券中標記解決版本？
- [ ] 6. 將所有變更（含版本號與更新日誌）一併 commit。
